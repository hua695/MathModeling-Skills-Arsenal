# Universal Modeling Contract v1

本文档是 `contest-orchestrator` 的通用建模约束。它与题型 profile 配合使用：通用约束保证推理链、证据链和交付一致性，profile 只增加本题型真正需要的检查，不把某一题型的做法硬套到所有题目。

## 1. 七项不变量

1. **问题到模型**：每个子问题必须说明题目条件、数据和输出如何映射到变量、参数、目标或状态。
2. **假设可审计**：每条假设同时写出“做了什么简化”和“由此产生的误差/适用边界”，并在模型评价中回顾。
3. **公式有来源和推导**：区分题目给定、文献采用和本文推导；本文推导须保留关键中间步骤、单位、边界和近似条件。标准教材公式可引用并说明适用条件，不要求重复证明。
4. **符号唯一**：新符号首次出现即定义，全文符号、单位、上下标一致，并进入符号表。
5. **算法可复现**：不得只报算法名称；必须说明选择理由、初始化/搜索区间、约束处理、终止条件、异常或局部最优处理。
6. **结果有可靠性**：主要结果不能只有单点；需给出误差/置信/残差、扰动或敏感性证据，并区分理论效应与算例中必须纳入的效应。
7. **闭环可追溯**：正文公式、算法和图表必须能追溯到代码、数据和注册表；附录代码实现正文关键逻辑，模型评价回扣适用边界。

## 2. 6.x 子问题固定模板

每个子问题在“模型建立与求解”章内先用一段不编号文字说明任务、已知条件、关键困难、输出目标及前后问关系，再设置两个编号小节：

1. `模型建立`：组织建模思路、必要的路线依据、假设与机理、局部首次使用的符号、原始关系、逐步推导、目标/状态关系和约束/边界；变量即时定义、公式编号并在行文引用。推导完成后，在本小节末尾集中给出唯一的最终求解模型框。
2. `模型求解与结果分析`：说明求解器或迭代方法、初始化、参数依据、范围、终止条件、异常处理和局部最优/过拟合/奇异情况处理；随后给出中间量、主结果、单位、可复现实验来源、结果意义、可靠性证据和适用边界。子问题结果不得全部推迟到检验章。

“决策变量”“目标函数”“约束条件”“推导”“算法”“结果分析”等作为小节内无编号引导词。独立的灵敏度或稳健性小节仅在存在独立扰动数据、评价指标或稳定性证据时设置，否则并入结果分析。上述证据必须完整，但不得把任务卡字段直接改写成清单式正文。

模型原理图、求解流程图、主拟合图和原始求解结果图优先放在本节；扰动、残差和敏感性对比放在模型检验章。

## 2.1 可执行证据载体

上述要求不能只靠关键词自检。每个子问题必须在 `model_contract.yaml` 登记证据卡，字段包含
`status`、正文 `text_anchors` 和可复现 `source_files`；`check_model_evidence.py` 会把锚点限制在该
子问题正文范围内，并按 `primary_capability` 与 `capabilities` 合并题型必需字段。正文中的每个
`eq:` 标签必须在 `derivation_registry.yaml` 登记；`derived` 公式至少有一个前置公式和两步正文推导。
严格交付运行证据图和推导链检查，卡片填 `true` 但没有正文锚点不能通过。该层验证“是否留下可审计
证据”，数学推导本身仍由 Critic 逐式复核，不把文本扫描冒充数学证明。

### 增强证据模式

新生成的 `model_contract.yaml` 使用 `schema_version: "2.1"` 和
`evidence_quality: enhanced`。在兼容旧项目的前提下，增强模式为每个子问题增加三项跨题型证据：

1. `route_comparison`：至少说明一个候选路线、最终选择和舍弃/不采用的理由；只有一条合理路线时，也要说明为什么不需要第二条路线。
2. `algorithm_card`：至少覆盖算法适配理由、初值或搜索范围、约束处理、终止条件，以及局部最优、过拟合或奇异情况的处理。
3. `intermediate_results`：至少给出一个能连接模型和主结果的中间量，例如粗估计、参数表、迭代收敛量、阶段性预测或可行性检查。

增强检查不是全文关键词计数：证据段落需要达到最低信息密度，并命中多个不同语义组；证据卡仍必须提供正文锚点，来源文件必须位于项目根目录内。旧的 v1.0 契约继续按兼容模式运行并报告迁移提示，不会被静默伪装成增强 PASS。

## 2.2 建模—求解前置输入契约

在生成模型建立与求解正文前，项目必须提供 `modeling_solution_contract.yaml`，由
`scripts/check_modeling_solution_contract.py` 核验：赛题小问、模型假设来源、变量清单、已调试代码逻辑和结果权威来源。
每个小问必须登记 `original → rearranged/intermediate → final` 公式链、每条公式的编号/正文锚点/含义说明、
与符号表的变量映射、算法选择理由、软件、全部关键参数及取值依据、外部结果文件。结果策略固定为
`numeric_results_policy: external_only`；求解章节不直接写未经结果文件核验的数值，完整代码放附录。
严格模式缺少任一前置输入、公式链、三线符号表、参数依据或结果来源即 BLOCK，并输出八项生成后自检清单。

## 3. 题型 profile 适配

| profile | 必需证据 | 不强制的内容 |
|---|---|---|
| `mechanistic_optimization` | 机理映射、路线比较、目标/约束、算法卡、中间结果、结果可靠性；机理反演至少两条独立路线交叉印证 | 不要求所有优化题都做解析路线 |
| `data_prediction` | 数据划分、预处理、基线模型、路线比较、超参数、指标、残差/泛化和敏感性 | 不要求两条解析反演路线 |
| `evaluation_decision` | 指标针对性、候选方法比较、正逆向/归一化、权重来源、排序结果、权重敏感性 | 不要求物理推导 |
| `simulation_dynamics` | 状态/守恒方程、初值/边界、数值方法、中间状态、步长/求解器敏感性、稳定性 | 不要求分类预测的 train/val/test |
| `hybrid` | 子问题接口、各子模型证据、组合约束、综合结果和鲁棒性 | 由子模型决定是否需要两条路线 |

“至少两条独立路线”只对机理反演类适用；解析/直接计算与数值拟合是常见组合。独立路线不应是同一代码的换名，必须能解释差异来源。

## 4. 门禁语义与证据登记

- `PASS`：所需证据存在且来源可读。
- `WARN`：非阻断缺项或无法在线核验，必须在报告中显示。
- `BLOCK`：缺少题型必需证据、模型章节比例低于强制阈值、正文出现内部交付文本或关键结果不可追溯。
- `UNKNOWN`：工具无法判断，不能转化为 `PASS`；严格模式下按阻断处理。

建议项目保存以下可选证据文件：`model_assumptions.md`、`symbol_table.md`、`equation_registry.json`、`algorithm_cards.yaml`、`results/`、`sensitivity_results.json`、`figure_registry.json`。文件不存在时默认报告 `WARN`，严格模式可配置为 `BLOCK`。

## 5. 正文比例与边界

模型建立与求解是全文核心，默认正文结构占比目标 45%--55%，低于 42% 阻断；实际页数优先于字符数，工具无法取得 PDF 文本位置时必须标注使用结构字符测量，不能伪称页数测量。模型检验只写事后扰动、残差、交叉验证、鲁棒性和误差分析，不重新讲模型选型。

## 6. B060 结构借鉴规则

可借鉴优秀论文的“路线比较—推导—算法—中间结果—主图—小结”证据顺序；不得复制其题目、数据、结论或版面。每个子问题求解后立即落结果，复杂推导和完整源码进入附录，但不得把关键建模逻辑全部移出正文。
