# 任务范围路由

主控技能先判断“用户要完成什么”，再决定加载哪些阶段。默认选择最小能够满足请求的范围；只有用户明确要求全流程或正式交付时，才升级到完整门禁。

机器执行入口：

```text
python scripts/scope_router.py --prompt "用户原话" --workspace <项目根> --out scope_plan.json
```

`scope_plan.json` 包含输入证据、范围、严格度、允许阶段、禁止动作和 `plan_digest`。后续 `delivery_all.py` 若接收 `--scope-plan`，必须验证摘要、范围和输入门状态；手工改写计划会被阻断。

## 范围枚举

| 范围 | 典型触发 | 允许加载 | 默认严格度 | 禁止自动扩展 |
|---|---|---|---|---|
| `PLAN_ONLY` | 先理解、给计划、拆题、选模型、列风险 | A1、A1.5、A2、A5，以及相关模型路由 | `STANDARD` | 不跑完整求解、论文、replay、交付门禁 |
| `SUBPROBLEM` | 求解问题2、敏感性分析、检查某个公式、出一张数据图 | 用户点名的子问题阶段及其直接依赖 | `STANDARD` | 不强制生成整篇论文、固定数量图表或全套交付产物 |
| `FULL_CONTEST` | 开始建模、全流程、完整论文、正式提交 | A–G 全链路和完整门禁 | `STRICT` | 不跳过强制门禁，不把示例结果当真实结果 |
| `DELIVERY_AUDIT` | 审 PDF、检查一致性、模拟评审、找版面问题 | F4、F4.x、F5 和被点名的审计项 | `STANDARD` | 只读审计，不重新建模或修改用户文件 |

## 判定顺序

1. 用户显式指定 `PLAN_ONLY`、`SUBPROBLEM`、`FULL_CONTEST` 或 `DELIVERY_AUDIT` 时，严格使用该范围。
2. 没有显式指定时，根据动词和交付物推断：
   - “理解、分析、规划、选模型、先不要写论文” → `PLAN_ONLY`；
   - “求解、计算、敏感性、出图、改一个章节” → `SUBPROBLEM`；
   - “开始建模、全流程、完整论文、正式提交” → `FULL_CONTEST`；
   - “审计、检查、找问题、模拟评审” → `DELIVERY_AUDIT`。
3. 仍然无法判断时，选择较小范围，并用一句话说明：“当前按 X 范围执行；如需完整交付可升级为 FULL_CONTEST。”

## 输入门

- `PLAN_ONLY` 没有题面或附件时可以继续做抽象计划，但必须标记“未读取真实数据”。
- `SUBPROBLEM`、`FULL_CONTEST` 需要题面或用户提供的结果文件；缺失时停止求解，列出缺失文件，不得虚构变量、数据或结果。
- `DELIVERY_AUDIT` 需要 PDF、LaTeX、DOCX 或结果目录中的至少一种证据；没有证据时只能输出审计清单，不能声称已通过检查。

`DELIVERY_AUDIT` 的正式入口是 `python scripts/audit_project.py <项目根> --out audit_report.json`。它把项目复制到隔离临时目录后执行审计，原项目只读；不编译、不重绘、不改论文。

## 严格度切换

- `STANDARD`：只执行当前范围的必要检查；警告不自动升级为全流程。
- `STRICT`：适用于正式竞赛交付；所有强制产物、引用、图表、PDF 和稳定路径门禁必须通过。
- 用户明确要求“只审计、不修改”时，即使当前为 `STRICT`，也不得写入论文或项目文件。

`STANDARD` 不是“无门禁”，而是范围收缩后的硬门禁：适用范围内的必检项仍必须通过，失败必须停在当前范围并报告原因。

## 范围—门禁矩阵

| 范围 | 最小硬门禁 | 不自动执行 |
|---|---|---|
| `PLAN_ONLY` | 输入完整性（或明确标记缺失）、假设/变量可追溯、计划输出完整 | 求解、论文、图表、交付 PDF 门禁 |
| `SUBPROBLEM` | 代码可复现、单位/边界/数量级检查、结果来源登记、针对性敏感性或可行性检查 | 全文引用、完整附录、全套 PDF/DOCX 门禁 |
| `FULL_CONTEST` | A–G 全阶段产物、结果一致性、图表来源、文献、PDF、稳定路径和交付门禁 | 无，除非用户明确降级范围 |
| `DELIVERY_AUDIT` | 证据存在性、文本层、页数、引用、版面和门禁状态可复核 | 重新求解、重绘、改论文、覆盖原文件 |

门禁失败处理：停止当前范围 → 记录 `FAIL` 与证据 → 给出修复动作；不得用缩小检查范围、改登记表或重复运行来伪造 `PASS`。

## 升级条件

只有以下情况可以从较小范围升级：

- 用户明确提出完整论文、正式提交或全流程；
- 当前子问题的结果依赖尚未建立的全局结果注册表；
- 用户确认接受新增的运行时间、文件产物和审计范围。

升级前必须先说明新增阶段、产物和副作用；不得静默启动完整流程。
